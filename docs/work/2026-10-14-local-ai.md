## 1. Named models in legion.json, picked per operator

**Outcome**: A folder can list named models in `legion.json`, each with a
harness, an optional address and a model. An operator's `model` in
`operator.json` can name one of them. Legion reads and checks the list, and
can say which harness, address and model any operator runs on. Sessions
still start exactly as today (draft 7 uses the answer).

**Why**: "Each operator gets two settings: Program … Model: which model that
program uses, picked from a named list in `legion.json`."

**Rules**:
- `legion.json` takes `"models": { "<name>": { "harness": "…", "address": "…", "model": "…" } }`, as in the doc's example.
- "An operator picks one of the named models. The harness comes with it."
- `harness` and `model` are required in each entry; `address` is optional.
- An entry with harness `claude-code` and an address is refused: Claude Code takes no address.
- Entry names follow the operator-name rule: lowercase letters, digits and dashes.
- An operator's `model` that names an entry resolves to that entry.
- An operator's `model` that names no entry (`opus`, `sonnet`, `haiku`) runs on Claude Code with that model, as today.
- No `models` in `legion.json` and no `model` in `operator.json`: Claude Code with its default model, as today.
- A broken `models` list fails loud when `legion.json` is read, naming the entry and the problem.
- Changing a folder's settings (`legion setup init --check …`) keeps `models` as it was.

**Done when**: Unit tests show: the doc's `legion.json` example parses; each
of the four resolutions above (named entry, plain Claude name, nothing set,
missing entry fields) gives the expected harness/address/model or error; and
`set_settings` leaves `models` untouched.

## 2. Harness templates in `.legion/harnesses/`

**Outcome**: Legion reads harness templates from `.legion/harnesses/<name>.json`
and can fill one in: given the blanks' values, it returns the command, its
arguments and its environment, ready to run. Nothing starts from them yet
(draft 7 does that).

**Why**: "Starting: one config template per harness … Adding a harness means
adding a template, not changing legion's code."

**Rules**:
- A template has `name`, `command`, `args`, optional `env`, and `tools`: `mcp` or `commands`, as in the doc's examples.
- `name` must match the file name; a mismatch fails loud.
- `claude-code` is built in: a `claude-code.json` file is refused, saying Claude Code is started by Legion itself.
- Blanks are `{name}` inside any argument or env value; Legion "fills in the `{blanks}` and runs the command".
- Known blanks: `firstPrompt`, `systemPromptFile`, `model`, `modelProvider`, `address`, `toolsConfig`, `toolsConfigFile`, `permissionMode`.
- A template using an unknown blank is refused when it's read, naming the blank and the file.
- An `args` item may be a list of strings: the whole list is left out when any blank in it has no value (for example `["--permission-mode", "{permissionMode}"]` with no mode set).
- A single-string argument whose blank has no value fails loud at fill time.
- No `.legion/harnesses/` folder is fine: Claude Code still works as today.

**Done when**: Unit tests show: the doc's OpenCode and Pi templates parse
(after `{harnessConfigFile}` is dropped, see notes); filling them gives the
expected command, args and env; an unknown blank, a name mismatch and a
`claude-code.json` are each refused with a clear message; a group with an
empty blank is left out.

## 3. The `report` tool: a session says what it's doing

**Outcome**: A session that has no Legion add-on can tell Legion it's
working, done or stuck, through Legion's tools. Legion shows that as the
session's state (busy, idle), the same way it shows a Claude session's today.
Claude Code sessions don't see the tool and behave as today.

**Why**: "Config can't say whether a session is busy or idle. Instead, the
session reports it through legion's tools ('working', 'done', 'stuck'), so it
works the same in every harness."

**Rules**:
- A new tool `report` takes `state` (`working`, `done` or `stuck`) and `text`, as in `legion report working "running the db checks"`.
- `working` makes the session busy; `done` makes it idle; `stuck` makes it idle and sends the text to the commander.
- The text becomes the session's detail, shown next to its state.
- The first report marks the session as one Legion can see (no more "can't see this session's state").
- A session whose add-on reports for it is refused: "this session's add-on already reports its state".
- The tool server lists `report` only to sessions started without the add-on, so Claude Code sessions see the same tools as today.
- The tool is named `report`, not `status`: "`legion status` is already taken".

**Done when**: Unit tests show the state mapping, the refusal for an add-on
session, and that `tools/list` has `report` only when the self-reporting
switch is set. A test on the daemon shows a session marked self-reporting
going starting → busy → idle on reports, with a log entry to the commander
for `stuck`.

## 4. Plain `legion` commands for every tool

**Outcome**: Inside a session Legion started, every Legion tool also works as
a shell command: `legion handoff`, `legion ask`, `legion done`, `legion
callout` and the rest. A harness that can only run shell commands (Pi) can
do everything a Claude Code operator does through MCP.

**Why**: "Plain commands, for harnesses that can only run shell commands …
These don't exist yet. For example `legion handoff --to reviewer "..."` and
`legion ask "..."`, using the same three settings."

**Rules**:
- One subcommand per tool in `TOOLS`, named after it with dashes (`flag_decision` → `legion flag-decision`).
- Each tool argument is a flag of the same name (`--mission`, `--next`, `--note`); required arguments can also be given in order without flags: `legion handoff 3 reviewer "built it"`, `legion ask "which port?"`.
- A command goes through the same `command_for_tool_call` as MCP, so the same checks and errors apply.
- It speaks for the session through the three settings already in its environment: `LEGION_DEPLOYMENT`, `LEGION_POSITION`, `LEGION_SOCKET`.
- Outside a session it refuses: "runs inside a session legiond started (LEGION_DEPLOYMENT isn't set)".
- Where a tool's name is already a `legion` command (`send`, `log`, `answer`), the existing command stays; it already speaks for the session when run inside one.
- The reply prints as the MCP tool's text does; an error exits non-zero.
- Commands for tools the caller's role can't use still parse; legiond refuses them, as it does over MCP.

**Done when**: Unit tests show argument parsing for flags and in-order
values, the refusal outside a session, and that every tool in `TOOLS` except
the three taken names has a subcommand. On a throwaway Legion, with the env
set to a running operator's position, `legion handoff <n> reviewer "x"` adds
the handoff entry to `legion log` from that position.

## 6. JSON Schema for legion.json, operator.json and harness files

**Outcome**: Each of Legion's config files has a JSON Schema. A `$schema`
line in the file gives editor checks and completion, and the schemas match
what Legion accepts.

**Why**: "Types: JSON Schema, not TypeScript … A schema with one type per
harness gives editor checks and catches mistakes, without adding a new
language to legion."

**Rules**:
- Three schemas: `legion.json` (including `models`), `operator.json`, and a harness file.
- The harness schema has one type for each `tools` route, so a `commands` template and an `mcp` template are each checked for what they need.
- `legion setup init` writes the schemas into `.legion/schemas/`, so `$schema` can be a relative path that works offline: `"$schema": "./schemas/harness.json"` (`../../schemas/…` from an operator folder).
- Every file Legion reads accepts a `$schema` field (`legion.json` and harness files too, not just `operator.json`).
- Anything the schema accepts, Legion accepts, and the other way round, for every example in `LOCAL_AI_FEATURE.md` (with the doc's `https://legion/schemas/…` URLs swapped for the relative paths).

**Done when**: A test validates the doc's examples and the starting setup
against the schemas, and parses the same files with Legion's own types; a
file with a wrong type or an unknown field fails both.
