harness, an optional address and a model. An operator's `model` in

**Rules**:
- `legion.json` takes `"models": { "<name>": { "harness": "…", "address": "…", "model": "…" } }`, as in the doc's example.
- "An operator picks one of the named models. The harness comes with it."

- No `models` in `legion.json` and no `model` in `operator.json`: Claude Code with its default model, as today.
- A broken `models` list fails loud when `legion.json` is read, naming the entry and the problem.
- Changing a folder's settings (`legion setup init --check …`) keeps `models` as it was.

## 2. Harness templates in `.legion/harnesses/`

**Outcome**: Legion reads harness templates from `.legion/harnesses/<name>.json`
and can fill one in: given the blanks' values, it returns the command, its
arguments, its environment, and any config file the harness needs written
for the session. Nothing starts from them yet (draft 5 does that).

**Why**: "Starting: one config template per harness … Adding a harness means
adding a template, not changing legion's code."

**Rules**:
- A template has `name`, `command`, `args`, optional `env`, and `tools`: `mcp` or `commands`, as in the doc's examples.
- An optional `configFile` is a JSON value Legion writes to a file for each session, with its blanks filled in both keys and values. The file's path fills the `{configFile}` blank. OpenCode needs this to get a session's own MCP server and provider (see draft 3).
- An optional `toolName` says how the harness shows Legion's tools to the model, with a `{tool}` blank, e.g. `"legion_{tool}"`. Claude Code's is `mcp__legion__{tool}`.
- `name` must match the file name; a mismatch fails loud.
- `claude-code` is built in: a `claude-code.json` file is refused, saying Claude Code is started by Legion itself.
- Blanks are `{name}`; Legion "fills in the `{blanks}` and runs the command".
- Known blanks: `firstPrompt`, `systemPromptFile`, `model`, `modelProvider`, `address`, `toolsConfig`, `toolsConfigFile`, `configFile`, `permissionMode`, `legionCommand`, `deployment`, `position`, `socket`, `workingFolder`.
- A template using an unknown blank is refused when it's read, naming the blank and the file.
- An `args` item may be a list of strings: the whole list is left out when any blank in it has no value (e.g. `["--permission-mode", "{permissionMode}"]` with no mode set).
- A single-string argument whose blank has no value fails loud at fill time.
- No `.legion/harnesses/` folder is fine: Claude Code still works as today.

**Done when**: Unit tests show: a template in the doc's shape, with a
`configFile` holding an `mcp` block and a provider block, parses; filling it
gives the expected command, args, env and config file text; an unknown
blank, a name mismatch and a `claude-code.json` are each refused with a
clear message; a group with an empty blank is left out.

---

Notes for the build:
- New `crates/legiond/src/harness.rs`: owns `HARNESSES_FOLDER_NAME = "harnesses"`, `HarnessTemplate`, `ToolRoute { Mcp, Commands }` (serde lowercase), `ArgumentItem` (untagged: `One(String)` | `Group(Vec<String>)`), `read_harness(folder, name)`, `harness_names(folder)`, and a pure `fill(template, &Blanks) -> Result<FilledCommand, String>`. `FilledCommand { command, args, env, config_file: Option<String> }`; draft 5 writes the file and sets `{configFile}`. Templates accept `$schema`.
- `Blanks` is a struct of `Option<String>` fields, one per known blank, so the known list has one owner.
- `modelProvider` is filled from the model entry's name (`spark-fast`); Joe's OpenCode config uses the same names as provider IDs.
- `legionCommand` is the full path of the `legion` binary next to legiond (`binary_folder.join(NAME)`), the same command `legion_tools_config` uses; `deployment`, `position` and `socket` are the three settings the tool server needs. With them, a `configFile` can describe Legion's tool server in the harness's own MCP format.

## 6. Plain `legion` commands for every tool

**Outcome**: Inside a session Legion started, every Legion tool also works as
a shell command: `legion handoff`, `legion ask`, `legion done`, `legion
callout` and the rest. A harness that can only run shell commands can do
everything a Claude Code operator does through MCP.

**Why**: "Plain commands, for harnesses that can only run shell commands …
These don't exist yet. For example `legion handoff --to reviewer "..."` and
`legion ask "..."`, using the same three settings."

**Rules**:
- One subcommand per tool in `TOOLS`, named after it with dashes (`flag_decision` → `legion flag-decision`).
- Each tool argument is a flag of the same name (`--mission`, `--next`, `--note`). Required arguments can also be given in order without flags: `legion handoff 3 reviewer "built it"`, `legion ask "which port?"`.
- A command goes through the same `command_for_tool_call` as MCP, so the same checks and errors apply.
- It speaks for the session through the three settings already in its environment: `LEGION_DEPLOYMENT`, `LEGION_POSITION`, `LEGION_SOCKET`.
- Outside a session it refuses: "runs inside a session legiond started (LEGION_DEPLOYMENT isn't set)".
- Where a tool's name is already a `legion` command (`send`, `log`, `answer`), the existing command stays; it already speaks for the session when run inside one.
- The reply prints as the MCP tool's text does; an error exits non-zero.

**Done when**: Unit tests show argument parsing with flags and in order,
the refusal outside a session, and that every tool in `TOOLS` except the
three taken names has a subcommand. On a throwaway Legion, with the
environment set to a running operator's position, `legion handoff <n>
reviewer "x"` adds the handoff entry to `legion log` from that position.

## 7. The `report` tool: a session says what it's doing (spare)

**Outcome**: A session with no Legion add-on tells Legion it's working, done
or stuck, and Legion shows it busy or idle, as it does a Claude session.
Claude Code sessions don't see the tool.

**Why**: "Config can't say whether a session is busy or idle. Instead, the
session reports it through legion's tools ('working', 'done', 'stuck'), so it
works the same in every harness."

**Rules**:
- A new tool `report` takes `state` (`working`, `done` or `stuck`) and `text`, as in `legion report working "running the db checks"`.
- `working` makes the session busy; `done` makes it idle; `stuck` makes it idle and sends the text to the commander.
- The text becomes the session's detail. The first report marks the session as one Legion can see.
- A session whose add-on reports for it is refused: "this session's add-on already reports its state".
- The tool server lists `report` only to sessions started from a template, so Claude Code sessions see the same tools as today.
- Template sessions count against `maxBusySessions` while busy, like any other.
- Template sessions' instructions tell them to report when they start and finish work.

**Done when**: Unit tests show the state mapping, the refusal for an add-on
session, and that `tools/list` has `report` only when the self-reporting
switch is set. A daemon test shows a template session going starting →
busy → idle on reports, with a message to the commander for `stuck`.

---
