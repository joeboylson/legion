## 1. The envelope and its names, in legion-proto

**Outcome**: `legion-proto` has the envelope: one Rust type for every
action, result and event, with a `noun.verb` name for each of today's
commands, replies and events, and a conversion from today's `Command` to an
action. Its TypeScript version is generated for the app. `docs/actions.md`
lists every name. Nothing uses it yet.

**Why**: "Every action, result and event is one envelope", and Joe's
decision 1: "Every `Command`, `Reply` and `Event` moves to the envelope and
its `noun.verb` names in one go, CLI and app included." The later drafts all
build on these types.

**Rules**:
- The envelope has `v` (1), `id`, `at` (milliseconds since 1970), `type` (`action`, `result` or `event`), `name`, `actor`, `subject`, `data`, `cause`, `reply_to` and `outcome`, as in the doc.
- `id` is a ULID: "unique and sortable; adapters drop repeats by it".
- `actor` has `kind` (`admin`, `session`, `legion`, `remote`), `machine`, `deployment`, `position` and `via` (`cli`, `app`, `mcp`, `addon`, `web`, `channel:<adapter>`, `hook:<name>`).
- `subject` has `folder`, `deployment`, `mission`, `part` and `position`: "the IDs it's about go in `subject`", and hooks match on them.
- `data` is "the action's own fields, typed per name in legion-proto".
- Names are `noun.verb`; events are in the past tense: "`mission.finished`".
- "`MissionFinish` is `mission.finish`, `SessionStart` is `session.start`, `Post` is `entry.post`."
- "`legion mission finish` already reads as `mission.finish`": each `legion <noun> <verb>` command maps to the action `<noun>.<verb>`. Where today's words and a command don't line up, `docs/actions.md` says which word wins (see notes); draft 8 renames the command to match.
- Today's replies become the `ok` of a result's `outcome`; an error is `{ "error": "…" }`.
- Today's events get past-tense names: `entry.added`, `session.changed`, `channels.changed`, `channel.logged`, `setup.changed`.
- New names the later drafts need are listed now: `session.report`, `entry.delivered`, `hooks.trust`, `hooks.status`.
- A round trip through JSON gives back the same envelope, for every name.

**Done when**: Unit tests show: every `Command` variant converts to an
action whose name is in `docs/actions.md`, with its IDs in `subject`; each
envelope survives a JSON round trip; the doc's two JSON examples (the
envelope and the builder's handoff) parse; a ULID made later sorts after
one made earlier. `npm run types` writes the new TypeScript files.

## 2. Reading `hooks.json`, and which folders are trusted

**Outcome**: legiond can read a folder's `.legion/hooks.json` and the
machine's `hooks.json` in its data folder, check them, and say whether a
folder's hooks may run: only when the machine settings list the folder with
the fingerprint of its current `hooks.json`. Nothing runs hooks yet.

**Why**: Decision 2: "Hooks run only in trusted folders. Trust lives in
Legion's machine settings … never in the repo." Both kinds of hook (drafts
10, 11) read their settings from here.

**Rules**:
- A hooks file has `hooks.before` and `hooks.after`, each a list of `{ match, when?, timeoutSeconds?, onTimeout?, hooks: [{ type, … }] }`, as in the doc.
- Hook types: `command` (`command`), `http` (`url`) and `adapter` (`adapter`). Anything else is refused when the file loads, naming it.
- "A `before` hook must name the actions it runs on (`mission.finish`), or narrow `*` with a `when` (`via: "web"`). A bare `"*"` with no `when` is refused when the file loads."
- `timeoutSeconds` defaults to 10. `onTimeout` defaults to "`block` for actions from outside the machine (`via: "web"`, `channel:*`), `allow` for everything else".
- A `before` hook can't be an `adapter`: "A hook can only allow or block an action".
- `match` takes a name, or a name with `*` (`mission.*`, `*`).
- Trust: `settings.json` holds each trusted folder with "a fingerprint (SHA-256) of its `hooks.json`".
- "If the file changes, Legion asks again, as `direnv allow` does": a fingerprint that doesn't match means not trusted.
- "Until then the folder's hooks don't run."
- "Machine-wide hooks in Legion's own data folder are trusted by being there."
- No `hooks.json` means no hooks, and nothing to trust.
- A broken `hooks.json` fails loud, naming the file and the problem, and runs none of its hooks.

**Done when**: Unit tests show: the doc's example file loads; a bare `*`
`before` hook, an unknown hook type and a `before` adapter hook are each
refused with a clear message; defaults fill in; a folder is trusted only
with a matching fingerprint, and untrusted after one byte of its file
changes; the machine's own file is trusted with no entry; `settings.json`
with a trust list parses and an unknown setting is still refused.

## 7. The action record

**Outcome**: Every action, result and event that goes through the door is
written to the folder's action record, `actions/<YYYY-MM-DD>.jsonl` in its
data folder, as the last step. legiond can read the record forward from a
saved place, which is what hooks and adapters will do.

**Why**: "Every envelope is written to a record that only grows … Writing it
is the last step of an action, so a written envelope is one that happened."
Decision 4: "one file per day in each folder's data".

**Rules**:
- Where: `~/.local/share/legion/folders/<name>-<hash>/actions/<YYYY-MM-DD>.jsonl`, one envelope per line.
- An action is written after it has run, with its result straight after it.
- Events are written as they're sent to watchers.
- An action with no folder (`folder.list`, `channel.open`) goes in the machine's record, `~/.local/share/legion/actions/`.
- Reads are left out of the record: "Do reads fire hooks? Proposed: no by default" (see notes).
- Each reader (a hook or an adapter) has a place: the day file and line it has handled up to, and that envelope's `id`. Places are kept on disk, so a restart picks up from them.
- Reading from a place gives every envelope written after it, in order, across days.
- "Local hooks on this machine see whole envelopes": the record holds them whole.
- A record that can't be written is printed to legiond's output and doesn't fail the action.

**Done when**: Unit tests show a write, a read from a place across two day
files, and a place surviving a reopen. An integration test on a throwaway
legiond: `mission.add` then `mission.list` leaves the `mission.add` action,
its result and its `entry.added` event in today's file, and no
`mission.list`.

- Open: which day a line goes in. Assumed UTC (from `at`), so no day repeats or goes missing at a clock change.

## 9. Session reports and deliveries as envelopes (add-on and OpenCode)

**Outcome**: What a session says about itself comes through the door as a
`session.report` action from that session, and each message handed to a
session is recorded as an event, whether the session is Claude (the
add-on's two routes) or OpenCode (Legion asking and posting to its server).
OpenCode's step lines are `entry.post` actions from the session.

**Why**: "Add-on reports become `session.report` actions from the session,
with `via: "addon"`. Inbox deliveries become `entry.added` events for that
session." OpenCode sessions now report and get messages through their own
server, so those paths need it too.

**Rules**:
- An add-on report is a `session.report` action: `actor.kind: "session"`, `via: "addon"`, the session's deployment, position and mission in `subject`, the report's fields in `data`.
- An OpenCode session's state, read from its server, is the same action with `via: "opencode"`.
- A report that changes nothing (same state and detail) isn't an action: OpenCode is asked every few seconds.
- Each entry handed to a session, by the add-on's inbox or posted to an OpenCode server, is recorded as an event naming that session in `subject.position`, with the `entry.added` event as its `cause`.
- An OpenCode step line is an `entry.post` action from the session, `via: "opencode"`.
- The add-on's routes and what they carry don't change: the add-on runs live from this repo.
- Entries a report leads to (a permission question) carry the report as `cause`.

**Done when**: Integration tests (`addon_connections.rs`,
`opencode_messages.rs`), watching events: a posted add-on report goes
through the door as a `session.report` action; a repeated identical report
gives nothing; a message taken by the inbox and one posted to a fake
OpenCode server each give a delivery event whose `cause` is the message's
`entry.added`. (Draft 7, in the same wave, writes them to the record.)

---

Notes for the build:
- `server.rs` (`receive_addon_report`, `hand_out_deliveries`), `daemon.rs` (`record_activity`, `take_deliveries`, `mark_handed`), `opencode_watch.rs` (`apply_opencode_answer`), `opencode_push.rs` (`record_pushed`), `opencode_events.rs` (`log_step`).
- Open: the doc says deliveries "become `entry.added` events for that session", but `entry.added` already fires when the entry is posted. Assumed: a delivery is its own event, `entry.delivered` (draft 1 names it), with `entry.added` as its cause.
- Open: `via` for OpenCode. The doc's list has no value for it. Assumed: a new `opencode` value (draft 1 adds it).
- A Claude session ends its `entry.delivered` at the moment the inbox answers, as `mark_handed` does today.

## 10. Channel messages are envelopes, through the channel permissions

**Outcome**: Messages between deployments on different machines travel as
envelopes. One arriving from another machine comes in as an action from
`actor.kind: "remote"`, `via: "channel:tcp"`, goes through the deployment's
receive switch (free, ask, off) as channel messages do today, and through
the door. One whose sending machine doesn't match the connection it came
in on is turned away.

**Why**: Decision 5: "Envelopes arriving from another machine go through the
same send and receive permissions channels use today … channel messages
become envelopes too, so there is one way in. Every remote envelope carries
its sending machine, and the receiver checks it against the channel it came
in on."

**Rules**:
- `Relay` carries an envelope instead of `from`, `to` and `text`: a `channel.send` action with the sender's machine, deployment and position in `actor`.
- `Undeliverable` carries the envelope that didn't get through and why.
- Hello, welcome, ping and the deployment list stay as they are: they keep the link up, they aren't actions.
- On arrival: `actor.machine` must be the machine that said hello on that connection (or, at the host, the subscriber it passed through); otherwise it's turned away and logged.
- On arrival, `actor.kind` is set to `remote` and `via` to `channel:tcp`, whatever was sent.
- Then the receive switch: `free` lets it in, `ask` holds it as a question, `off` turns it away and tells the sender, as today.
- The send switch works as today on the way out.
- A host passing a message on between two other machines passes the envelope unchanged.
- The two ends say a version in their hello; an end on another version is refused with "the other end runs a different Legion version".

**Done when**: Channel tests (`channels.rs`, `channel_wire.rs`): a message
sent from one test Legion reaches the other's commander, with the
arrival's envelope in the receiver's record as `remote`; a relay whose
`actor.machine` isn't the connection's is turned away; each switch setting
does what it does today; an old-version hello is refused.

---

Notes for the build:
- `channel_wire.rs` (`WireMessage::Relay`, `Undeliverable`, `Hello` with a version), `channels.rs` (`hand_over`, `send`), `channel_delivery.rs` (`take_from_channel`, `send_on_channels`), `channel_gate.rs`, `channel_holds.rs` (holds keep the envelope).
- `channel.send` text is the envelope's `data.text`, sent whole: decision 4's text limits are for adapters (draft 15); draft 17 decides how TCP fits them.
- The flaky `channels::tests::a_wrong_key_is_turned_away`: rerun before blaming the change (callouts).

## 11. `before` hooks: allow or block, with a time limit

**Outcome**: A trusted `before` hook runs on each action it matches, before
the action runs. Exit 0 lets it through; exit 2 blocks it, and what the hook
wrote to stderr goes back to whoever sent it. A slow hook holds up only its
own action.

**Why**: "`before` is like Claude Code's `PreToolUse`." Decision 3:
"`before` hooks only allow or block. No changing an action."

**Rules**:
- "The hook gets the envelope as JSON on stdin. Exit code 2 blocks the action, and what it wrote to stderr goes back to whoever sent it."
- Any other exit code lets it through, with a note in the log naming the hook and the code (assumed; Claude Code treats other codes as non-blocking).
- An `http` hook gets the envelope as the body of a POST; a 2xx lets it through, a reply of `{ "decision": "block", "reason": "…" }` blocks it (assumed shape).
- A hook never changes the action: what it writes to stdout is ignored.
- "Each has `timeoutSeconds` (default 10) and `onTimeout`: `block` stops the action and says the hook timed out; `allow` lets it through and writes a note to the log."
- "`before` hooks run outside legiond's state lock, so a slow one holds up only its own action, not other folders or sessions."
- "Legion's own actions (`actor.kind: "legion"`) don't run `before` hooks unless a hook names them."
- Only trusted folders' hooks run (draft 2); the machine's always run.
- Matching uses the action's name, `when` and `subject`: the doc's examples.
- A blocked action is in the record as the action and an error result naming the hook.
- Hooks for one action run one after another, in file order, the machine's first; the first block stops the rest.

**Done when**: Integration tests on a throwaway legiond with a trusted
folder: a hook on `mission.finish` that exits 2 with "CI is red" makes
`legion mission finish` fail with "CI is red"; a hook that sleeps past
`timeoutSeconds` blocks with `onTimeout: block` and lets through with a log
note with `allow`; while it sleeps, `mission.list` in another folder
answers at once; a check-in from Legion isn't blocked by a `*` hook with
`when: { via: "web" }`; an untrusted folder's hook doesn't run.

---

Notes for the build:
- New `before_hooks.rs` (match, run with a time limit, decide); `door.rs` calls it before the match, without holding `state`. Run commands with `sh -c` in the folder, env `LEGION_HOOK` (its name); draft 16 adds the cause.
- The door runs on a blocking thread (`spawn_blocking` in `server.rs`), so a blocking wait is fine there; Legion's own actions come from tokio tasks too, so don't block a runtime thread: check where `act_as_legion` is called from.
- `http` hooks: legiond already speaks HTTP with `hyper` (`opencode_server.rs`); plain `http://` only until draft 18 brings TLS. Fail loud on `https://` until then.

## 12. `after` hooks: read the record, each from its own place

**Outcome**: Each trusted `after` hook reads the action record in the
background from its own place and runs on each envelope it matches. A slow
or failing hook delays no other hook and never Legion. After a restart or
the machine sleeping, each catches up from its place.

**Why**: "`after` is like `PostToolUse`. It sees the result or event and
can't block it. It reads from the action record, not from the action as it
happens."

**Rules**:
- "`after` hooks and adapters each read the record from where they left off, in the background. Each keeps its own place … so a slow Supabase adapter never delays a TCP one, and neither delays Legion."
- "After a restart, a crash or the machine sleeping, each picks up from its place and catches up. Nothing is lost."
- "A hook that keeps failing is retried with a growing wait, then marked stuck in the app, with its place kept, so you can fix it and let it catch up."
- A `command` hook gets one envelope as JSON on stdin and succeeds with exit 0; an `http` hook gets it as a POST and succeeds with a 2xx.
- `session.key` and `session.input` reach an `after` hook only when it names them: "kept out of `after` hooks and adapters unless named."
- A new hook starts from the end of the record, not its beginning (assumed: it's for what happens from now on).
- `hooks.status` gives each hook's place, whether it's stuck and why.
- An `adapter` hook is skipped until draft 15, with one note in the log.

**Done when**: Integration tests: an `entry.added` hook writes each event
to a file, once each, in order; a hook that fails three times is retried
with longer waits and shows stuck in `hooks.status`; after legiond
restarts, a hook that was behind catches up and handles nothing twice; a
hook that sleeps doesn't delay a second hook's file.

---

Notes for the build:
- New `record_reader.rs`: one reader per place, following the day files (waits for new lines; no busy loop). Shared by adapters in draft 15. New `after_hooks.rs`: the runner and its retries. `main.rs`: start the readers.
- Growing wait: assumed 1 s doubling to 5 min; stuck after 10 failures in a row on one envelope. Each reader keeps its place at the failing envelope.
- A hook that's taken out of `hooks.json` keeps its place on disk (it may come back).

## 13. Keeping the record: 14 days, 500 MB, never ahead of a reader

**Outcome**: Old day files of the action record are deleted after 14 days,
but never before every `after` hook and adapter has read past them. If the
record grows past about 500 MB, the oldest days go anyway, and a reader that
hadn't read them is marked "fell behind".

**Why**: Decision 4: "Kept 14 days, and never deleted before every `after`
hook and adapter has read past it; capped at about 500 MB, oldest days
first. An adapter that falls behind the cap shows as 'fell behind' in the
app."

**Rules**:
- A day file older than 14 days goes once every reader's place is past it.
- When the folder's record is over 500 MB, the oldest day files go until it's under, whatever the readers' places.
- A reader whose place was in a file that went is marked fell behind and moves to the oldest file left; `hooks.status` says so.
- Today's file is never deleted.
- Each deletion goes in legiond's output, and a fell-behind reader in the log for the admin.

**Done when**: Unit tests with a fake clock and small sizes: a 15-day-old
file goes when no reader needs it; stays while one does; over the cap the
oldest go and the reader behind is marked; today's file stays even when
it's over the cap alone.

---

Notes for the build:
- New `record_retention.rs` (pure: which files go, which readers fell behind). `action_record.rs` runs it when it starts a new day's file, so no new task in `main.rs`.
- Open: the cap per folder or for the whole machine. Assumed per folder's `actions/` folder.
- Constants (14 days, 500 MB) owned in `record_retention.rs`.

## 15. Adapters, and what may leave the machine

**Outcome**: legiond has adapters: each reads the action record from its own
place and sends what it may to somewhere else, and hands over what comes
back. Before anything leaves, a filter keeps it to what decision 4 allows.
A test adapter shows it working; TCP and Supabase come in 17 and 18.

**Why**: "An adapter needs only `send(envelope)` and a stream of incoming
envelopes." Decision 4 sets what may leave the machine.

**Rules**:
- An adapter is configured as an `after` hook of type `adapter`, naming it (`"adapter": "supabase"`), with its own settings.
- "By default an adapter sends only what happened and to what (`name`, `actor`, `subject`, `at`, `id`, `cause`), no text."
- "Each adapter lists the action names it may send (`"send": ["mission.*", "entry.added"]`), and text fields (`data`) go only with `"includeText": true`."
- An adapter with no `send` list sends nothing.
- "`session.key` and `session.input` never leave the machine", whatever the adapter's settings say.
- Results and events count by their name, as actions do.
- Incoming envelopes "arrive as `actor.kind: "remote"`, `via: "channel:<adapter>"`" and go through the channel permissions and the door, as in draft 10.
- An adapter keeps its place, retries and goes stuck as an `after` hook does, and can fall behind (draft 13).

**Done when**: Unit tests on the filter: no `send` list sends nothing; a
listed name goes without `data`; with `includeText` it goes whole;
`session.input` never goes, even when listed as `*` with `includeText`. An
integration test with a test adapter writing to a file: the right
envelopes, filtered, once each, caught up after a restart.

## 16. No loops: a hook's actions carry its cause

**Outcome**: An action a hook causes (a hook that runs `legion send`) carries
the hook's envelope as its `cause` and `via: "hook:<name>"`. Legion refuses
one that would loop.

**Why**: "Legion refuses an action whose `cause` chain already passes
through the same hook on the same subject, and any chain deeper than 8. The
refusal goes in the log, naming the hook."

**Rules**:
- A hook's process gets its envelope's `id` and its own name in its environment; the `legion` command run inside it sends them as `cause` and `via: "hook:<name>"`.
- An `http` hook's request carries them as headers, and an action sent back with them is treated the same.
- The door follows `cause` back through the record: if the chain passes the same hook on the same subject, the action is refused.
- A chain deeper than 8 is refused.
- "The refusal goes in the log, naming the hook."

**Done when**: An integration test: an `after` hook on `entry.added` that
runs `legion send` to the same position sends once, and the second round
is refused with a log entry naming the hook; a chain of 9 different
hooks stops at the ninth.

---

Notes for the build:
- `door.rs` (the chain check), `before_hooks.rs` and `after_hooks.rs` (env `LEGION_CAUSE`, `LEGION_HOOK`; names are constants in `legion-proto` beside `ENV_DEPLOYMENT`), `legion-client` (reads them).
- Following the chain reads the record backwards by `id`; keep a small in-memory index of recent `id`s to `cause`s rather than scanning files.

## 17. Channels send from the record, through the TCP adapter

**Outcome**: The TCP channels are an adapter: a commander's message to
another deployment is written to the record first, and the TCP adapter
reads it from its place and sends it. A message sent while the channel was
down goes out when it comes back.

**Why**: The doc's step 4: "TCP channels moved behind an adapter that reads
the record."

**Rules**:
- `channel.send` is recorded by the door, then sent by the TCP adapter reading from its place.
- The TCP adapter is built in and always on while a channel is open; it needs no entry in `hooks.json`.
- Its send list is `channel.send` with text: the text is the message. Nothing else goes.
- A message that can't go now is kept at the adapter's place and sent when the channel is back, in order; the sender is told it's waiting, not that it failed.
- The adapter drops an arriving envelope whose `id` it has already handed over.
- Undeliverable messages come back as today.

**Done when**: Channel tests: a message sent while the subscription is down
arrives once it's back, once; an arriving repeat `id` is dropped; nothing
but `channel.send` crosses (a test reads what the other end got).

Notes for the build:
- New `tcp_adapter.rs` implementing draft 15's trait over today's connections; `channels.rs` loses its direct `send` path; `channel_delivery.rs` (`send_on_channels` only records).
- Open: decision 4's default is no text, but a channel message is only text. Assumed: the TCP adapter's built-in send list is `channel.send` with text, and nothing else; flagged for Joe.

## 18. The Supabase adapter

**Outcome**: A folder (or the machine) can send its record to Supabase
through an `after` hook of type `adapter`, `"adapter": "supabase"`, within
decision 4's limits, and take in envelopes from other machines the same way
channels do.

**Why**: The doc's step 5.

**Rules**:
- Built to draft 3's finding: its table, login and incoming path.
- Sends only what draft 15's filter lets through: by default no text.
- A repeat `id` is dropped on both ends.
- Incoming envelopes go through the channel permissions and the door as `remote`, `via: "channel:supabase"` (draft 10).
- The key lives in the machine's settings or the keychain, never in `hooks.json`.
- Works through a sleep and a restart without sending anything twice.

**Done when**: Tests against a local Supabase (or the finding's stand-in):
the filtered envelopes arrive once each, an incoming one reaches a
commander, and a restart sends nothing twice.

---

Notes for the build:
- New `supabase_adapter.rs`; `adapters.rs` registers it. Needs an HTTPS client (draft 3 says which).
- Split if draft 3 shows sending and receiving are each a session's work.
